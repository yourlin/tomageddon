## 1. 目标与边界

支持按角色、怪物、精英、Boss 和章节逐个替换外部美术；同一局可以同时出现程序化 Rig、静态插画和逐帧动画。缺少或加载失败的素材使用现有程序化形象，不能影响开局、战斗或旧存档。

最终应能通过素材文件和清单接入新美术，无需为每个实体修改战斗代码。头像、选角动态展示、战斗、分身及技能里的角色展示采用一致的外观解析规则。

本轮框架包含：透明静态贴图、规则精灵表、带裁切信息的图集、现有动作状态映射、皮肤与词缀外观、地图贴图和按需加载。武器、弹幕和 UI 的全量重画，以及 Spine / Live2D / 3D 动画接入另行规划。章节漫画按 [STORY.md](STORY.md) 和现有漫画场景继续运行。

## 3. 技术方案

### 3.1 统一视觉对象

新增 `EntityVisual`（暂定名）与 `createEntityVisual` 工厂，采用逐个调用点迁移的方式，保留 `Rig` 作为程序化实现。

所有视觉实现以 Phaser Container 作为外层，保持位置、深度、缩放、透明度、可见性和场景生命周期的一致语义；内部可挂载 Rig 或 Sprite。工厂输入必须是结构化的 `kind + id + skinId + variant`，不能依赖拆分 `enemy_xxx_champ` 等字符串识别身份。

需要兼容现有调用的能力：

- `play(state, force)`、`tick(dt, moveAmount, face, lookX, lookY)`、当前 `state`。
- `setRadius`、`setStatusTint`、`resetVisual`、`die(callback)`。
- Phaser 的位置、深度、可见性、激活、缩放、透明度、销毁和容器绘制行为。
- 阴影、朝向、受击反馈、冻结和眩晕等公共视觉效果。

先审计所有 `new Rig`、`Rig` 类型注解和对 `puppet` / `bodyImg` 等内部成员的访问；业务逻辑不应依赖某种渲染实现的内部部件。

碰撞半径、伤害、攻击预警、子弹生成、掉落和 Boss 转阶段继续由现有玩法系统决定。贴图的透明边距、可见大小、播放速度均不能修改这些数值。

### 3.2 外观选择与回退

建议按以下顺序选择外观：

1. 清单中声明的精确实体、皮肤和变体素材。
2. 清单明确声明可复用的基础素材，配合受支持的调色或配饰方案。
3. 对应皮肤 / 变体的原有程序化 Rig。

未声明兼容时，不能用基础插画悄悄覆盖已购买皮肤，也不能把词缀精英显示成普通怪物。玩家皮肤的 ID、价格、解锁和存档结构保持兼容。词缀精英现有的金色辨识效果需要保留或提供等效边框 / 光环。

“实体没有任何可用素材”与“选中的动画缺某个动作”分别处理：前者回退 Rig，后者使用该实体的静态帧与通用反馈，避免动作中途切换成另一种画风。

### 3.3 素材清单与规范

建议新增 `src/data/artManifest.ts` 作为类型化入口，配套校验脚本。以下目录和字段是拟议规范，不是已经可用的接口。

```text
src/assets/entities/char/tomato/
  portrait.png
  body.png
  motion.png
  motion.json
src/assets/entities/enemy/maggot/
src/assets/entities/boss/<id>/
src/assets/maps/ch1/
  ground.webp
  foreground.png
```

| 项目 | 规范 |
|---|---|
| 身份 | `kind`、实体 `id`、可选 `skinId` 和 `variant`，均校验对应数据定义 |
| 模式 | `procedural` / `static` / `spritesheet` / `atlas` |
| 资源 | 使用可被 Vite 分析的模块导入或固定目录 glob；禁止从任意运行时路径拼接构建资源 |
| 透明度 | 战斗实体使用带真实透明通道的 PNG / WebP，不带棋盘底和烘焙地面 |
| 画面 | 统一斜俯视角、主光源和轮廓；头像可单独导出，不直接使用漫画场景截图 |
| 锚点 | 明确地面接触点与视觉偏移；待机和动作帧沿用同一参考点 |
| 缩放 | 记录美术参考半径及显示倍率，区别于玩法碰撞半径 |
| 方向 | 首期左右翻转，声明原始朝向；非对称装备需明确是否允许镜像 |
| 规则精灵表 | 帧宽高、间距、边距、帧范围与播放规则；帧间留边防止采样串色 |
| 图集 | 支持帧名、裁切前尺寸和裁切偏移，首期禁用旋转打包，避免动作锚点漂移 |
| 动画 | 状态、帧列表、帧率、循环、播放速度适配策略及缺失动作处理 |
| 皮肤 | 精确素材、可复用基础素材的声明，或显式回退 Rig |
| 版本 | 清单 schema 版本和资源版本，用于缓存失效和问题定位 |

先用小范围试点确定像素尺寸，建议从普通角色单帧 256×256、Boss 单帧 512×512 开始比较清晰度与显存；不将这些候选尺寸作为全量强制标准。

加载器要区分普通单图、规则精灵表和图集，同一文件只能由一个加载入口负责。当前全目录图片扫描需要排除新实体 / 地图目录，交给清单管理，避免提前把精灵表当普通图片加载，以及不同目录中同名 `body.png` 相互覆盖。

### 3.4 动作状态与时序

现有状态完整覆盖：`idle`、`move`、`attack`、`hurt`、`windup`、`charge`、`stun`、`die`、`spawn`、`cast`、`victory`、`frozen`。

- `idle`、`move` 循环；同一状态的重复调用默认不重启动画，保留 `force` 的重播语义。
- `attack`、`hurt`、`spawn`、`cast` 等一次性反馈结束后恢复正确的基础状态，不能覆盖冻结、死亡或更高优先级反馈。
- `windup`、`charge` 与 Boss 技能时序同步。不能为了播完插画动画延迟伤害或缩短预警；允许调整动画速度或保持末帧。
- `frozen` 固定当前姿态并显示冻结反馈；`stun` 保留可辨识的眩晕效果。解冻 / 解控后继续正确状态。
- 缺少某动作时，使用基准帧配合呼吸、弹跳、受击闪白、旋转或淡出；缺少死亡帧也必须完成回收。
- 玩法死亡回调与图集是否成功加载、是否存在动画完成事件解耦，确保只执行一次；暂停时遵循游戏时间，避免暂停中提前回收。
- 对象回池时停止动画和 tween、解除完成监听、清除回调、染色、翻转、透明度和临时特效，避免下一只怪物继承上一只的死亡状态。

### 3.5 地图与资源生命周期

地图清单记录章节、世界坐标参考、画面边距与显示范围，复用现有 `mapPlacement`。地面与前景分层；角色、掉落、弹幕和危险预警必须清楚可见。

障碍物美术与 `ArenaDef` 的几何位置对齐；外部图片不能自动改变通行区域。保留程序化的碰撞调试叠层，并验证 Boss 动态区域变化与美术遮罩一致。静态地图不适合表达的机关、临时障碍和预警继续由游戏单独绘制。

头像与首屏资源优先加载；进入章节前加载当前角色、皮肤、章节怪物池、召唤物、精英 / Boss 池及地图；暂不在启动时下载全部高分辨率动画。章节外的分身 / 召唤来源也要纳入依赖解析。

纹理由资源管理器维护引用，实体回收不等于卸载纹理。卸载前检查活跃场景、对象池、图集动画和头像缓存引用，避免返回选角后黑图。加载失败提供可重试状态，修复或重试后能够失效旧的回退头像缓存。

合计约 **10–17 人日工程工作量**，排期建议预留约 20% 返工缓冲。M1 的静态验证可先独立完成；前面讨论的“2–4 人日试点”仅适用于小范围静态 / 轻量动效验证，不代表完整框架和第一章全部动态素材交付。

### 试点素材范围

先制作番茄妹的静态战斗图、头像和少量动作；再加入第一章实际怪物池、一位 Boss 和平底锅地图。需要额外选择至少一种带腿 / 翅膀 / 非圆身体的实体，验证接口没有只适配圆形主角。

第一章 Boss 有随机池：试点只替换一位，其余明确回退 Rig。完成框架后再逐个补齐，不能以“某次随机到已换图 Boss”作为整章覆盖完成的依据。

## 5. 验收与发布门槛

### 功能与兼容性

- [ ] 仅程序素材、仅静态插画、完整动画、混合素材四种组合均能运行。
- [ ] 缺图、坏图集、缺帧、重复 key、未知实体和资源下载失败有明确诊断；不会阻塞开局。
- [ ] 所有原有状态都可显示；攻击预警、伤害发生时间、冻结、眩晕与死亡回收不受动画长度影响。
- [ ] 连续回收再生成、强制切换动作、暂停 / 恢复和场景销毁不会重复掉落、泄漏监听或遗留不可见实体。
- [ ] 角色头像、动态展示、战斗、分身 / 技能外观一致；皮肤和词缀变体符合显式回退规则。
- [ ] 旧存档载入、已购皮肤和解锁记录正常，不需要重新购买或重置存档。
- [ ] 七章地图边界、障碍、出生点与动态区域变化吻合；章节缩略图显示正确。
- [ ] 中英文界面、首次开局、重开、换角色 / 皮肤、切章和返回选角均无黑图。

### 性能与验证方式

M0 在同一设备、相同章节、怪物数量、游戏种子和画质设置下记录程序版基线，分别覆盖常规战斗与高密度场景；同时记录首次加载和缓存后加载。

建议试点门槛：p95 帧耗时相对基线增长不超过 15%，正常性能设备仍满足目标帧率；低内存设备无崩溃、无持续增长的纹理 / 监听数量。若设备已经低于目标帧率，必须说明基线与差值，不能只给平均 FPS。绝对显存与首屏包体上限在 M0 实测后确定。

验证分为三层：清单与帧定义的静态校验；动画状态、回调和资源引用的自动化测试；真实浏览器 / Steam 构建中的战斗、对象池压力与视觉截图检查。至少覆盖桌面浏览器、一个低内存移动设备与 Steam 构建。

基础检查沿用 `npm run typecheck`、`npm test`、`npm run lint`、`npm run build`；补充清单校验命令、固定种子压力场景和截图检查脚本。生产构建检查资源路径、按需加载和图集是否误入首屏。

## 6. 扩量顺序与制作交接

1. 完成第一章试点与四位剧情主角设计基准，固定视角、比例、颜色和动作模板。
2. 按章节迁移普通怪物和地图，再补该章全部精英 / Boss；每章保留覆盖报告。
3. 补齐剩余可玩角色、独特动作和特殊身体结构。
4. 按皮肤明确登记“独立素材 / 已支持复用 / 程序回退”，再决定哪些值得单独重画。
5. 覆盖、性能与视觉验收完成前保留 Rig；清理程序美术作为单独决策。

每批交付应包含素材、清单条目、参考图 / 提示词、生成或制作来源、动作覆盖表和游戏内预览。AI 生成素材先检查真实透明度、帧间身份一致性、脚底锚点和裁切偏移；不能把生成的整张动作拼图直接当成已校准的动画精灵表。

工程支持完成不等于 187 个基础设计完成。全量静态 / 轻量动画美术及接入可参考此前 **15–30 人日**的粗估；完整逐帧动画约 **40–60+ 人日**，均不含 156 套皮肤全部独立制作。实际排期需在 M5 后依据试点的每实体制作、返修和接入时间重新估算，避免与本框架估算重复相加。

## 7. 首个可执行里程碑

优先完成 **M0 + M1**：一个透明番茄妹、一种怪物、一张现有地图的替换入口，以及无素材时的 Rig 回退。验收时并排查看新旧形象，验证碰撞和攻击时序一致；随后再投入全量生图和逐帧动画制作。
